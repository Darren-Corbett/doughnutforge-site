# Site audit, 24 October 2026

The live site (https://doughnut-forge.app, deployed from `99d31ff`) and a local build of the same source, checked after the owner reported eight problems on launch day plus one. Nothing on the site was changed for this audit. The fixes are proposed separately, for approval.

## How it was checked

| Check | Where | Coverage |
|---|---|---|
| Layout (`npm run test:layout`, `tests/layout/layout.spec.ts`) | Chromium, WebKit (desktop) | All 246 pages (245 in the sitemap plus the 404) in all 30 languages, at 360, 390, 768, 1280 and 1440px, light and dark |
| Layout, phone | WebKit with the iPhone 13 profile (mobile viewport, touch, meta viewport) | All 246 pages at 360, 390 and 430px, light and dark; again at 320 and 375px (iPhone Display Zoom) |
| What each layout check measures | | Elements past the screen edge; sideways scroll or pan; the header links on one row (≤430px); every image loads; text wider than its box; links covering each other; the language menu open; the FAQ answers open |
| Accessibility (`tests/layout/a11y.spec.ts`) | Chromium, WebKit | axe-core, WCAG 2.2 A and AA, all 246 pages at 390 and 1280px, light and dark |
| Interactions (`tests/layout/interactions.spec.ts`) | Chromium, WebKit | Language menu in all 30 languages (links, current language, Escape, click outside, English-only pages); store badges on home, download and pricing in all 30 languages (badge language, alt text, link shape, image loads, new tab); FAQ; keyboard focus on 10 page types; the 404 page |
| Links (`npm run test:links`, `tests/links/links.spec.ts`) | Network | Internal links and `#fragments` in the build; every external link; live feed, sitemap, robots.txt, apple-app-site-association and 404; the forge-privacy redirect for every `?lang=` |
| Real Mobile Safari (`tests/ios/real-safari.ts`) | iOS Simulator through safaridriver | iPhone 16e (390pt), iOS 26.2: 86 pages in en, de, ru, el, fi, hu, ms, th, ja and vi, light and dark. iPhone 17 (402pt), iOS 26.2: 6 pages, dark. iPhone 16, iOS 18.0: `/download/`, dark |
| Lighthouse 12.8.2 | Live home page | Mobile and desktop |

Tool versions: Playwright 1.64.1 (Chromium 1248, WebKit 27.2), axe-core 4.14 through `@axe-core/playwright`, Xcode simulators with iOS 18.0 and 26.2.

**Limits.**
- Touch drags cannot be automated in the iOS Simulator: safaridriver's touch actions hang. Sideways pan in real Safari was therefore measured, not dragged. A page can pan only when its scroll width is greater than the screen, and the check reads the scroll width, `scrollX` after a scroll to the far right, and the visual viewport.
- Display Zoom cannot be switched on in the simulator by script, so it was reproduced with a 320px viewport in WebKit's iPhone profile.

**Lighthouse, live home page:** mobile 100 performance, 100 accessibility, 100 best practices, 100 SEO (LCP 1.0 s, CLS 0.011). Desktop 100 / 100 / 100 / 100 (LCP 0.4 s, CLS 0.002).

## High

### H1. Nothing checks that the live home page is the build just deployed (known issue 1)
- **Page:** `/` · **Language:** en · **Browser:** any · **Width:** any · **Theme:** any
- **Screenshot:** [01-live-home-390.webp](2026-10-24/01-live-home-390.webp) (the live home page now: the new site)
- **What happens now:** it does not reproduce. `https://`, `http://`, `www.` and `darren-corbett.github.io/doughnutforge-site/` all serve the new home page (last modified 23 October, 14:31 UTC).
- **Cause:** the Actions history shows a branch-source "pages build and deployment" run at 13:54:24 UTC on `42fb02c`, between two Actions deploys. For about three minutes, from 13:54:57 to 13:58:14, GitHub Pages served the repo root, where `index.html` is still the "Coming soon" placeholder. A branch build has no `/download/` page, so a browser showing the old home page and the new download page together had kept `/` from that window. Safari restores open tabs and back-forward pages without asking the server.
- **Why it matters still:**
  1. The repo-root placeholder is the documented rollback until 6 November, so a rollback serves "Coming soon" again.
  2. The deploy job checks only `apple-app-site-association`, not the pages.
  3. The local build's `index.html` differs from the live one (sha256 `a8102d24` against `aeb17894`), because the deploy build adds social images for every language. A live check must compare with the deploy's own build, not a local one.
- **Suggested fix:**
  - The build job records the sha256 of `dist/index.html` and `dist/download/index.html`. After deploying, the deploy job retries until the live pages match, and fails if they never do or if `/` contains "Coming soon".
  - It also fails unless the Pages API reports `build_type: workflow`.
  - Replace the root placeholder `index.html` with a copy that links to the site, so a rollback no longer says "Coming soon" (to be approved: it changes the rollback).

### H2. Store links do not open in a new tab, and do not say so (known issue 5)
- **Pages:** `/`, `/download/`, `/pricing/` · **Languages:** all 30 · **Browsers:** Chromium, WebKit · **Width:** any · **Theme:** any
- **Screenshot:** [02-ios26-download-dark.webp](2026-10-24/02-ios26-download-dark.webp) (the badges affected)
- **Found:** `<a href="https://apps.apple.com/app/id6812778888" rel="noopener">` with no `target`; the Microsoft link is the same. `tests/layout/interactions.spec.ts` fails 360 times, once per badge, page, language and engine.
- **Cause:** `src/components/StoreBadge.astro:31`.
- **Suggested fix:**
  - Add `target="_blank" rel="noopener noreferrer"` and visually hidden text after the badge's alt, such as "(opens in a new tab)".
  - The text is a new string in all 30 languages, reviewed and stamped like every translation.

### H3. The header links wrap at 320px, and are tight at 360px (known issue 8)
- **Pages:** every page · **Languages at 320px:** de, el, en, en-US, es, es-MX, ru, sv, uk · **Browser:** WebKit iPhone (and Chromium) · **Width:** 320 · **Themes:** both
- **Screenshots:** [08-en-home-320-nav.webp](2026-10-24/08-en-home-320-nav.webp) ("Support" on a second row), [08-uk-home-360-nav.webp](2026-10-24/08-uk-home-360-nav.webp) (Ukrainian at 360px, 3px from wrapping)
- **Found:**
  - At 360 to 430px every language fits on one row, in Chromium, WebKit and real Safari. At 390pt in real Safari the tightest is Russian, with 47px to spare.
  - Below that the links wrap. English needs 330px, German 340px and Russian 343px.
  - Space left at 360px, tightest first: uk 3px, es and es-MX 16, ru 17, de 20, el 24, sv 25, en 32. Everything else has 40px or more.
- **Likely cause of the owner's report:** iPhone **Display Zoom** (Settings > Display & Brightness > Display Zoom > Larger Text) gives a 320pt screen on 375 and 390pt iPhones. Safari's page zoom (aA > larger text) narrows the page the same way. A 390pt iPhone at 115% zoom is about 340px wide.
- **To confirm on the owner's iPhone:** the model, the iOS version, whether Display Zoom is on, and the aA zoom level on doughnut-forge.app.
- **Suggested fix:** make all four links fit down to 320px in every language, rather than a 2×2 layout. Options:
  - gap and side padding that shrink with the screen;
  - the logo text hidden below 340px (the icon and its label stay);
  - link labels at 14px below 360px.
  
  The header test then checks 320px too.

### H4. With Display Zoom, the German support page pans sideways (known issue 7, partly)
- **Page:** `/de/support/` · **Language:** de · **Browsers:** WebKit iPhone, Chromium · **Width:** 320 · **Themes:** both
- **Screenshot:** [07-de-support-320-pan.webp](2026-10-24/07-de-support-320-pan.webp) (scrolled to the right: the question's box runs past the column and the page moves 28px)
- **Found:** the page is 348px wide in a 320px screen.
- **Cause:** the FAQ question "Was bedeutet Post-Quanten-Verschlüsselung?".
  - The middleware keeps the hyphenated word whole (`.keep-word`, `white-space: nowrap`) and sets `--longest:29` on the `h3`, correctly.
  - The global rule in `global.css`, which shrinks a heading so its longest word fits, never applies here: `Faq.astro` sets its own `h3 { font-size: 19px }`, and that scoped style wins.
  - At 19px, weight 800, the word is 292px wide. `min-width: min-content` keeps the `h3` at 302px, while the summary is 288px and also holds the 14px "+" and a 16px gap.
- **Suggested fix:** in `Faq.astro`, use `--fs: 19px` instead of a fixed font size, so the shared shrink rule applies, and leave room for the "+" icon. Do not hide the overflow. The same check should cover every component that sets its own heading size.

### M2. The pan on English `/features/` and `/pricing/` does not reproduce (known issue 7)

- **Found:** no element is wider than the screen, and the scroll width equals the screen width, at every width from 300 to 1440px, in WebKit's iPhone profile and in real Safari (402pt and 390pt). Each suspect was measured and none overflows:

- **Needed from the owner:** the screen recording, the iPhone model, the iOS version, Display Zoom on or off, the Safari aA zoom, and whether content blockers are on. If Display Zoom is on, H3 and H4 are the cause, and the fixes there cover it.

### M3. The Mac App Store badge renders in dark mode (known issue 2)
- **Page:** `/download/` · **Language:** en · **Browsers:** real Safari iOS 18.0 and 26.2, WebKit · **Width:** 390, 402 · **Theme:** dark
- **Screenshots:** [02-ios26-download-dark.webp](2026-10-24/02-ios26-download-dark.webp) (iPhone 17, iOS 26.2), [02-ios18-download-dark.webp](2026-10-24/02-ios18-download-dark.webp) (iPhone 16, iOS 18.0)
- **Found:**
  - The badge is drawn on every device and theme tested.
  - The badge test passes in all 30 languages in both engines: the file loads, has pixels and is the right language.
  - The SVG is Apple's own file, served as `image/svg+xml`, and no site CSS touches images.
- **Not ruled out:**
  1. A Safari content blocker or "Hide Distracting Items". Annoyance lists often hide links to `apps.apple.com`, which would explain why only the Apple badge went missing.
  2. A lazy image that had not loaded yet when the screen was captured.
  3. Lockdown Mode.
- **Needed from the owner:** a screenshot, the iOS version, and whether the badge shows in a private tab with content blockers off (long-press the reload button > Turn off Content Blockers).

## Low

### L1. The 404 page's `og:url` names a page that does not exist
- **Page:** `/404.html` (served for every unknown address) · **Language:** en · **Browser:** any · **Width:** any · **Theme:** any
- **Screenshot:** none (the tag is not shown)
- **Found:** `<meta property="og:url" content="https://doughnut-forge.app/404/">`. The page is `noindex`, so search is not affected, but a shared broken link would preview with a URL that does not exist.
- **Suggested fix:** leave `og:url` off the 404 page.

### L2. Without a country code, a browser off Apple devices can land on the US App Store page
- **Pages:** every page with the Mac badge · **Languages:** all · **Browser:** any browser that is not on an Apple device · **Width:** any · **Theme:** any
- **Screenshot:** none (this is a store redirect)
- **Found:** from a UK connection with `Accept-Language: en-GB`, `https://apps.apple.com/app/id6812778888` redirects to `/us/app/doughnut-forge-desktop/id6812778888?mt=12`. On a Mac, iPhone or iPad the link opens the App Store app in the visitor's own storefront, which is the case that matters.
- **Suggested fix:** none. The rule stays: no country code, so the site never promises a storefront. Recorded so the redirect is not mistaken for a bug.

## Notes

- **N1. iOS (known issue 4).** The owner confirmed on 24 October that the iOS App Store ID does not exist yet, so iOS stays "Coming soon". When it exists, the change is one line in `src/data/stores.ts`. These strings change with it, in all 30 languages:
  - `home.phones.title` ("Coming soon to iPhone and iPad.") and `home.phones.text`;
  - `meta.download.title` and `meta.download.description`;
  - `press.shots.text`;
  - four "which is coming soon" captions in two blog posts, with their `docs/BLOG-CLAIMS.md` rows.
  
  The press facts and the `SoftwareApplication` `operatingSystem` follow `stores.ts` on their own. App Store badges are already in place for every language that has one.
- **N2. Windows (known issue 3).** The owner confirmed the Microsoft Store link works. Automated checks cannot confirm it:
  - The store answers 403 to plain HTTP clients and to most headless browsers (bot protection), and blocked every visit after a few runs.
  - Pages that did load showed the app.
  - Every language's link has the right shape, `https://apps.microsoft.com/detail/9P25BS9L8LNB?hl=<language>`.
  
  The link test now reports a 403 as blocked and is skipped if every visit is blocked.
- **N3. apple-app-site-association.** The live file is served as `application/octet-stream` (GitHub Pages cannot set headers). Apple's CDN (`app-site-association.cdn-apple.com/a/v1/doughnut-forge.app`) has it, parsed as JSON, with both app IDs. No action.
